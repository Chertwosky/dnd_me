# MVP Specification

## 1. Product goal

Сделать платформу для онлайн-сессий D&D, где мастер и игроки могут играть в одной комнате, используя карту, токены, карточки персонажей, броски кубов, лут, события и встроенную справочную панель.

## 2. Product positioning

Продукт сочетает два сценария:

- **virtual tabletop** для ведения партии;
- **GM toolkit** для подготовки и управления сессией.

Главный принцип MVP: одна игровая сессия должна проходить внутри одного интерфейса без постоянных переключений между внешними сервисами.

## 3. Target users

### Dungeon Master

Потребности:

- быстро поднять комнату;
- загрузить карту;
- разложить токены;
- управлять правами игроков;
- запускать игровые механики без подготовки сторонних инструментов.

### Player

Потребности:

- зайти в игру без долгой настройки;
- понимать, что происходит на карте;
- двигать своего персонажа;
- открывать лист героя;
- видеть броски, лут и эффекты событий.

## 4. Core user flows

### 4.1 Создание комнаты мастером

1. Мастер авторизуется.
2. Создаёт комнату.
3. Получает invite-ссылку.
4. Загружает карту.
5. Настраивает сетку и размещает токены.
6. Приглашает игроков.

### 4.2 Присоединение игрока

1. Игрок открывает invite-ссылку.
2. Выбирает персонажа или получает привязанный лист.
3. Подключается к realtime-сессии.
4. Видит карту и свой токен.

### 4.3 Базовый цикл игры

1. Мастер двигает NPC или разрешает ход игроку.
2. Игрок двигает свой токен.
3. Любой участник кидает кубы.
4. Мастер открывает справку по монстру, предмету или заклинанию.
5. Мастер генерирует лут или случайное событие.
6. Система показывает результат в правой панели и логирует действие.

## 5. Functional requirements

### 5.1 Rooms & roles

#### MVP

- комната создаётся пользователем с ролью `gm`;
- подключение по invite-token;
- роли `gm`, `player`, `spectator`;
- проверка прав на сервере и клиенте.

#### Out of scope

- сложные ACL-матрицы;
- публичный каталог комнат;
- кросс-комнатные кампании.

### 5.2 Battle map

#### MVP

- загрузка одной карты на комнату;
- базовая сетка;
- pan/zoom;
- drag-and-drop токенов;
- координаты токенов синхронизируются между клиентами;
- измерение расстояния;
- слой fog of war как простые закрывающие области.

#### Acceptance criteria

- перемещение токена одним участником отображается у других менее чем за 300 мс при нормальной сети;
- игрок не может двигать чужой токен;
- мастер может двигать любые токены.

### 5.3 Character sheets

#### MVP

- JSON-модель для базовых характеристик;
- загрузка PDF/изображения как вложения;
- просмотр краткой карточки по клику на токен;
- редактирование владельцем и мастером.

#### Acceptance criteria

- у токена может быть связанный `characterSheetId`;
- при клике по токену открывается сайд-панель;
- изменение HP сохраняется и синхронизируется.

### 5.4 Dice system

#### MVP

- стандартные кубы d4–d100;
- текстовая команда `/roll`;
- лог бросков с автором, формулой, результатом и timestamp.

#### Acceptance criteria

- выражение `1d20+5` корректно парсится;
- результат сохраняется в БД;
- новые броски появляются у всех участников комнаты в реальном времени.

### 5.5 Loot generator

#### MVP

- таблицы лута комнаты;
- категории редкости и типа;
- генерация случайного результата;
- выдача в инвентарь персонажа или в сундук комнаты.

#### Acceptance criteria

- мастер может создать минимум одну пользовательскую таблицу;
- система генерирует минимум один `LootItem` с количеством и редкостью;
- факт выдачи логируется.

### 5.6 Random events

#### MVP

- таблицы событий по сцене;
- вес/вероятность выпадения;
- текст события и тип эффекта;
- запуск из интерфейса мастера.

#### Acceptance criteria

- мастер может выбрать таблицу `tavern`, `road`, `dungeon`, `forest`, `city`;
- после запуска в комнате появляется событие;
- событие записывается в журнал.

### 5.7 Knowledge base side panel

#### MVP

- единое поле поиска;
- фильтры по типам сущностей;
- результаты открываются в сайд-панели;
- контент не должен требовать ухода со страницы комнаты.

#### Acceptance criteria

- поиск выдаёт результаты по минимум пяти типам сущностей;
- открытая статья не закрывает карту;
- интерфейс работает независимо от источника контента.

## 6. Non-functional requirements

### Performance

- первое отображение комнаты: до 3 секунд при типовой карте;
- realtime-события должны доставляться почти мгновенно;
- карта должна быть пригодна для работы на десктопах и планшетах.

### Reliability

- сервер валидирует все права на изменение объектов;
- операции перемещения токена должны быть idempotent-friendly;
- состояние комнаты должно восстанавливаться после перезагрузки.

### Security

- invite-ссылки должны быть достаточно случайными;
- файлы должны храниться в приватном бакете с ограниченным доступом;
- редактирование карточек должно проверяться по роли и владению.

### Legal

- не копировать защищённый контент D&D без лицензий;
- строить MVP вокруг движка и пользовательского контента;
- использовать собственный или лицензируемый справочный материал.

## 7. UI structure

### Landing

- value proposition;
- CTA на создание комнаты;
- демонстрация основных сценариев.

### Room lobby

- список участников;
- выбор персонажа;
- настройки комнаты;
- переход в игру.

### Game screen

- центр: карта;
- слева: токены, инициатива, участники;
- справа: справка, карточки, лут, события;
- снизу: чат и броски.

## 8. Release milestones

### Milestone 1

- auth;
- rooms;
- battle map upload;
- tokens;
- realtime movement.

### Milestone 2

- character sheets;
- dice roller;
- chat.

### Milestone 3

- loot generator;
- random events;
- journal.

### Milestone 4

- fog of war;
- initiative;
- NPC helpers;
- searchable knowledge base.

## 9. MVP success criteria

MVP можно считать успешным, если команда может провести короткую D&D-сессию со следующими действиями внутри одной комнаты:

- создать комнату;
- загрузить карту;
- двигать фишки;
- открыть карточку персонажа;
- бросить кубы;
- сгенерировать лут;
- вызвать случайное событие;
- открыть справку в боковой панели.
